# 0045 — Discover: search GitHub from RepoMagpie

**Status:** accepted (2026-10-26). Adds to [0034](0034-the-mcp-server.md) without changing it: the MCP server still never uses the network.

## Context
RepoMagpie answers "what do I have for X?" from the user's own notes. When the answer is "nothing yet", the user leaves for GitHub's search, finds a few candidates, and comes back to paste each URL into `repomagpie note`. GitHub's search already filters by stars, activity, language, licence and topics; RepoMagpie knows which repositories the user has a note on, and the domains and kinds of [0030](0030-github-topics-become-tags.md) and [0040](0040-domains-a-second-axis.md). Discover puts the two side by side, and leaves adding to the path that already exists.

## Decision
1. **Where:** `repomagpie discover` in the CLI and a Discover page in the local app (`GET /api/discover`). **Not** in the MCP server: [0034](0034-the-mcp-server.md) promises that it reads the journals and never the network. An agent may run `repomagpie discover --json` through its shell; the skill says so in one line.
2. **The only new network use** is one GitHub search request (at most 3, or 2 without a token, rule 6) when the user searches: `GET https://api.github.com/search/repositories`, with the words and filters, and `GITHUB_TOKEN` when it is set. Nothing from the journals is sent. In the app, the server makes the request; the browser never calls GitHub, and the Content Security Policy is unchanged.
3. **Adding** is the existing `repomagpie note <url>` path (`POST /api/note` in the app), one note per repository, Verdict-less to the inbox unless the user types a Verdict. Discover never writes a note on its own.
4. **GitHub's text is untrusted** ([0032](0032-note-text-is-data.md)): descriptions, topics and names are cleaned and capped as note text is. A result's link is built from its `owner/repo` name, always `https://github.com/<owner>/<repo>`; a result whose name isn't one is dropped.
5. **The estimates are deterministic,** from the topics and the name, with no model: `estimated_kind` by 0030's rules that need no file (`kindFromTopics` in `src/core/github.ts`), `null` when only the repository's files could say; `suggested_domains` by 0040's. They are labelled "estimated".
6. **Domains and kinds become topics.** GitHub's search can't combine qualifiers with OR. Checked on 2026-10-26 with read-only requests: `topic:design-system OR topic:component-library stars:>=1000` is refused (422: "The search contains only logical operators (AND / OR / NOT) without any search terms. Logical operators only apply to text, not to qualifiers."), and with a word, `react topic:design-system OR topic:component-library` finds 0, while `react topic:design-system` finds 50 and the two topics together (an AND) 12. GitHub's docs, read again on 2026-10-27, don't say otherwise: the REST "Search" page names `AND`, `OR` and `NOT` only to limit a query to five of them; "Understanding the search syntax" describes `NOT` for words ("can only be used for string keywords") and a `-` before a qualifier to exclude it, and never mentions `OR`; "Searching for repositories" shows `topic:` with one topic. No page describes matching any one of several topics in one query. So:
   - a domain is one request for each of its 3 most common topics, and the results are merged, one per repository, and sorted again;
   - the topics are, of those `DOMAIN_MAP` maps to the domain on its own (not `ai`, nor `playwright`), the 3 with the most repositories of 10 stars or more, counted on 2026-10-26 with one search each (`DOMAIN_TOPICS` in `src/core/discover.ts`);
   - a kind that topics name (`skill-pack`, `awesome-list`, `template`, `platform`, `framework`) is searched by those topics; one with a single topic joins each of a domain's requests;
   - the other kinds (`library`, `cli`, `plugin`, `app`, `other`) are told apart by files GitHub's search can't see: the results are filtered by their estimated kind, and the answer says the filter is approximate. So is a kind with several topics beside a domain, to keep to 3 requests;
   - without a token, a domain or kind sends only its first 2 topics, and a warning names the one left out: GitHub allows 10 searches a minute then, and a search shouldn't spend a third of them;
   - the requests go one after another, never at once (GitHub's best practices: "make requests serially instead of concurrently" to avoid its secondary limits).
7. **Defaults:** at least 10 stars, pushed within 24 months, no archived repositories, no forks, sorted by stars, 20 results a page (at most 50). Words go with `in:name,description,topics`, GitHub's default made explicit. GitHub's own limits are kept: words of at most 256 characters, and pages within its first 1,000 results.
8. **A short cache:** the same search within 10 minutes is answered from `<personal journal>/.cache/discover.json` (the last 50 searches, written whole and renamed). Search allows 10 requests a minute without a token and 30 with one; paging back and forth, or the app reloading, shouldn't spend them. The token is never in the cache or its key. A rate-limited or failed answer is never cached, nor one a rate limit cut short (rule 9). The cache holds successful answers only, so what is read from it can answer a search but never fail one or keep it from GitHub: the file carries a version (2 since 2026-10-27), a file of another version starts empty, and each entry is checked field by field on read, an entry of any other shape dropped. An answer from the cache says so (`cached: true`, and one line in the CLI).
9. **Rate limits** follow GitHub's rules ("Rate limits for the REST API", read on 2026-10-27). A 403 or 429 with `x-ratelimit-remaining: 0` is the search limit (or the primary one), over at `x-ratelimit-reset`; another 403 or 429 that says so, or carries `retry-after`, is the secondary limit, its own problem (`secondary-rate-limit`). `retry-after`, when present, is how long to wait, before any reset time; `x-ratelimit-reset` is read only when the remaining count is 0. A time already past is never shown: the message says "try again in a minute", as GitHub's docs say to wait. A limit whose end is known and at most 60 seconds away is waited out, a second longer (GitHub's reset is in whole seconds), and the request is sent again, once a search: the CLI says so in one line before it waits, and the app stays loading. Without a token the minute's searches are shared by the address (Consequences), so a limit often ends within the minute, and a wait beats a failure the user must retry by hand. A longer or unknown wait, or a limit met again, isn't waited for: a search with no answers fails with the message, and when a later request of a search meets a limit, the search stops there and shows what the earlier ones found, with a warning; it isn't cached.

GitHub's facts, read on 2026-10-26 from docs.github.com: "Search" in the REST API (per page at most 100, at most 1,000 results, the sorts, the search limit of 30 requests a minute with a token and 10 without, query text of at most 256 characters), "Searching for repositories" (`in:`, `topic:`, `stars:`, `pushed:`, `language:`, `archived:`, `fork:`), and "Rate limits for the REST API" (403 or 429 with `x-ratelimit-remaining: 0`, the reset time, and `x-ratelimit-resource: search`). Read again on 2026-10-27: "Search" and "Understanding the search syntax" for `OR` (rule 6), "Rate limits for the REST API" for secondary limits and `retry-after`, "Best practices for using the REST API" for serial requests (rules 6 and 9).

## Consequences
- A third network request, after `note` and `import`: SECURITY.md lists it, and the README's privacy answer names it.
- A search for a domain costs 3 of the minute's searches with a token, 2 without. Without one, five such searches in a minute use the limit up; the answer names the reset time and how a token raises it, and a search cut short keeps what it found. A search can take up to a minute longer when it waits a limit out (rule 9); in the app, the server's one-search-at-a-time queue holds the next search for that long. A domain search without a token misses the repositories that have only its third topic; the warning says which topic.
- Found on Windows (2026-10-27, without a token): a domain search lost all its answers when its third request met the limit, and a message showed a reset time 3 minutes past. Reproduced with fake responses: the first by a fake GitHub that allows 10 searches a minute, the second by a secondary limit's 403 with `retry-after` beside a stale `x-ratelimit-reset`, which the message read first. Rule 9 is the fix. A retest the same day, with this code, reported a limit "until 14:54 UTC" with no results, while GitHub's `/rate_limit` showed the search limit unused; renaming `discover.json` seemed to fix it. That file held two well-formed successful entries, which this code skips once they are 10 minutes old, so it wasn't the cause; the cache was made strict anyway (rule 8).
- A live diagnostic the same day (2026-10-27, Windows, no token, `REPOMAGPIE_DEBUG_HTTP=1`, the maintainer's permission) found the cause. The first request of the first run, at 15:33:35 UTC, got a 403 with `x-ratelimit-limit: 10`, `x-ratelimit-remaining: 0`, `x-ratelimit-used: 10`, `x-ratelimit-reset` 15:34:08, `x-ratelimit-resource: search`, and "API rate limit exceeded for <the public IP address>". GitHub's `Date` matched the machine's clock. A second run 3 seconds later got the same. `curl.exe https://api.github.com/rate_limit`, at 15:33:39, showed the search limit with 0 used. No IPv6 and no proxy: curl and Node left from the same address. So without a token, the 10 searches a minute are counted for the public IP address, as GitHub's message says. The 10 used weren't the diagnostic's own, since it hadn't searched before that minute. Other programs or devices behind the same address (a home network, or an ISP's shared address) are the likely source. The headers don't say why `/rate_limit` showed curl none used. The "until" time is that answer's `x-ratelimit-reset`, about 30 seconds ahead, cut to the minute. The retest's "until 14:54 UTC" at 15:01 was the same field: the code then still printed the search limit's reset after it had passed, which rule 9 now forbids on every path. Two changes follow: a wait of up to 2 minutes is said in seconds, and the message says the 10 are shared by the address, with a token as the way to searches of one's own. The test `the live 403 on a search's first request` uses those headers. A search that met this limit failed, with no results; rule 9's wait and retry, added the same day, waits a limit like this one out. A second live check without a token, with the switch on, got 200 for both requests while `x-ratelimit-used` went from 1 to 4 in the half second between them, and a curl search right after also got 200: something else behind the address was searching at the same time, which confirms the shared count.
- `total` is the sum of the requests' counts, so a repository with two of a domain's topics counts twice. It is GitHub's estimate either way.
- The approximate kinds can return fewer results than the page size, and miss repositories whose topics say nothing. The answer says so each time.
- A domain's topics are a snapshot. They change only with a new count and a new record, like any other decision.
- Discover sees what GitHub's search sees: the description and topics, not the README. Its estimates can differ from what `note` decides once it reads the repository, its keywords and its README ([0046](0046-classification-signals.md)).
